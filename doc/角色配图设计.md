# 对话里的「角色发图」设计

> 状态：**已实现**（服务端协议 + 客户端出图与渲染）。Phase 4 切片 6b 之后落地。
> 本文只记决定与坑，不重复代码里已有的说明。

## 一、前提：输入侧已经做完了

「用户给角色发图」这条链**已经完整实现**，不是半成品：

| 环节 | 位置 |
| --- | --- |
| 输入框左侧的附图键 | `components/ChatPage.vue` 的 `aria-label="Attach an image"` |
| 选图 → 压到长边 1024 → 缩略图预览 / 可撤 | `shrinkForChat`、`attach` |
| 发送时把 Blob 一起交出 | `emit('send', id, text, blob)` |
| 图存 `chat_images`，消息上只挂 `imageId` | `sendChat` → `putChatImage` |
| **这一轮自动切到识图配置**，读回 Blob 转 data URL 一起发 | `runChat` |
| 历史里的图不重发（一张上千 token） | `chatStream({ images })` |
| 气泡渲染、导出/导入带图 | `bubble-img`、`ImportedChat.images` |

所以「多模态」要补的只有**输出侧**：角色 → 用户发图。

## 二、四个决定（已确认）

1. **图片来源：现场生成（C）**。不做「发自己的设定图」与「发已有作品」这两条零成本路线。
2. **生成的图只活在对话里**：**不进历史、不进作品集**。想收藏由用户自己下载。
3. **只在被要求或确实合适时发**：不是每句都配图。
4. **排期**：先把 Phase 4 切片 6b 收口，再动这个功能。

## 三、设计要点

### 协议：照搬 `[mood:xxx]` 那套

模型产出不了图片字节，只能产出**意图**，所以本质是「模型表达意图 → 客户端执行」。
本仓已有一个成熟先例：情绪标签（`server/index.js` 的 `splitMood`）——服务端负责剪掉、
流式期间扣留半截标签、`done` 事件里单独送字段。它已经解决了最难的两件事：
**标签绝不漏给用户看**、**流式中途不闪半截**。照搬它，不另造机制。

- 系统提示加一节：在回复最后单独一行写 `[photo:<场景描述>]`，并说明"不要解释这枚标签、
  也不要每句都发"。
- 服务端加 `splitPhoto`，与 `splitMood` 并排；`done` 事件多带一个 `photo` 字段。
- 客户端拿到 `photo` 后：**先出字、图位占一个固定比例的骨架**，图生成完再贴上。

### 必须处理的坑

1. **`CHAT_TAIL` 要重新算**。它现在按 `[mood:amused]`（13 字符）定的 24。
   场景描述比一个单词长得多，两枚标签还可能同时出现 —— 尾巴不够长就会在流式时
   漏出半截标签给用户看见。
2. **场景描述要限长 + 清洗**。它是模型写的自由文本，会进提示词、可能带引号/换行。
   要截断、去控制字符，并且**永远不当作指令**（只当一段被包装过的描述）。
3. **只认最后一枚**标签（与 mood 同一处剪），一轮最多一张图。
4. **频率兜底**：提示词里写"别每句都发"之外，客户端也要拦（例如连续 N 轮最多一张）——
   提示词约束不住模型。
5. **失败不阻断文字**：出图报错/超时就撤掉骨架，必要时一行小字说明，正文照旧。
6. **异步与流式的顺序**：图比文字慢得多。不能等图出来才显示文字，也不能让图到达时
   把已经读完的气泡顶下去 —— 骨架必须是固定比例。
7. **要用哪个配置出图**：当前生效的出图配置（`config`）。角色的设定图当参考图送进去，
   这是"同一张脸"的唯一保证（与 `genCharView` 同一条路径）。
8. **不进历史的落盘路径**：既然不进历史，就**不能**走 `persist()`（那是往历史里写的）。
   图字节存 `chat_images`（与用户附图同一张表），消息上挂一个**与 `imageId` 分开**的字段
   （`photoId`）—— 语义不同：一个是"对方发来的"，一个是"它给你的"，
   渲染位置、清理时机、撤销语义都不一样。
9. **导出/导入**：`photoId` 的字节要并进 `ImportedChat.images`（那里已经是
   `{ id, blob }[]`，"谁附的"不影响搬运）；标签本身随消息文本走，零改动。
10. **`types.ts` 里那句「只有用户消息会带 imageId」是文档约束**，加了输出侧之后要改。

### 与识图的合流

用户发图那一轮已经切到识图配置；若同一轮角色又回图，就是「识图模型看进来 + 出图模型
画出去」——两个配置各管一段。产品上最自然的场景（"你看我这张照片" → "（看了）……
我也来一张"）正好落在这条缝里，实现时**不要**把两条配置路径搅在一起。

## 四、验证方式（实现时）

- 服务端单测：`splitPhoto` 的剪取、白名单/清洗、半截标签的扣留（含两枚标签同时出现时
  的尾巴长度）。
- 浏览器探针：播种一条带 `photoId` 的助手消息 → 断言图**渲染在文字下方**、骨架占位
  不撑跳；再断言流式期间正文里**看不到**半截标签。
- 预算：这一条会新增一次出图调用，`--max-ms` 之类的门禁不受影响，但要确认
  **不阻塞首屏与流式**。


## 五、实现记录

- **服务端**（[server/chatTags.js](../server/chatTags.js)）：标签逻辑抽成独立模块，
  `splitTags` 一次剪下 mood 与 photo（两枚同时出现、顺序任意都认）；
  半截标签只擦不取，前缀放宽到 3 个字母（`[pho` 这种"正好停在半个词上"原来会漏出去）；
  `TAG_HOLD` 从 24 提到 160。12 条单测。
- **客户端**：`chatStream` 把 `photo` 从 `done` 事件带回；`runChat` 在收尾时
  **先挂场景描述**（界面立刻占骨架位）再后台画，画完存 `chat_images` 并挂 `photoId`；
  画失败就清掉标记，正文照旧。
- **出图**（`useGeneration.generateChatPhoto`）：场景在前、角色设定在后，
  角色的设定图当参考图；**刻意不走 `persist`/`recordFor`** —— 图只活在对话里。
- **渲染**：`.bubble-photo` 垫在文字**下面**（用户附图在上面），
  未完成时是固定比例的骨架。
- **验证**：对话探针播种"已画好"与"还在画"两条助手消息，断言
  **图渲染了、且在文字之后**、待画的显示骨架。九道门 + 170 条单测。

### 还没做的

- 频率兜底只写在提示词里（客户端还没拦）。
- 图进了 `chat_images`，但**导出/导入还没带上 assistant 的 `photoId`**
  （`ImportedChat.images` 已经能搬字节，只差把它收进去）。
