# 对话出图：构图、光影与「自拍 / 他拍」

> 状态：**已实现**（2026-10-04）。三批都已落地：第一批（锚点句 / 分层拼装 /
> 自拍他拍模板 / 尺寸与参考图按镜头挑）+ 第二批（**摄影指导层**，走已有的
> `/api/enhance`）+ 第三批（**放宽上限与动态扣尾**，见决定十）。
> 见文末「九、实现记录」。
> 协议扩展**已结案为不需要**（见 §五 与决定九）：视角改由摄影指导判，
> `photoSelf` 只回答"画面里有没有人"。
> 整条链有端到端探针兜着（`scripts/probe-chat-photo.mjs`，假上游、不花钱）。
> 仍未做：摄影指导的开关。
> 配套阅读：[角色配图设计.md](角色配图设计.md)（协议与落盘已经实现，本文只补出图质量这一层）。

## 一、问题

用户反馈原话：生成的图**非常死板**，没有光影、没有场景；说「自拍」出来还是**他拍**；环境和人物**融不到一起**。

这一篇要回答的不是"要不要调参"，而是**为什么这条路必然出这样的图**。

## 二、诊断：信息在哪一层丢的

一条链只有三处参与，全部在拼字符串，没有一处对"这张照片怎么拍"负责。

| 环节 | 位置 | 它实际交付了什么 |
| --- | --- | --- |
| 聊天模型写标签 | [server/index.js:174](../server/index.js#L174) | 一段 **120 字符以内**的"场景短描述"（**已放宽到 400**，见决定十） |
| 剪标签 | [server/chatTags.js:33](../server/chatTags.js#L33) 的 `PHOTO_SCENE_CHARS` | 再截一次 120（**已放宽到 400**）；`self:` 前缀**只用来定一个布尔**，剪掉 |
| 拼提示词 | [src/lib/chatPhoto.ts:41](../src/lib/chatPhoto.ts#L41) | `scene + ", " + characterFaceDesc`，上限 1200 字符（**已放宽到 6000**） |

`characterFaceDesc`（[src/api.ts:2104](../src/api.ts#L2104)）是 `CHAR_FACE_FIELDS` 的逐项枚举，出来是这样一个东西：

```
photorealistic, female, a night-shift nurse in a coastal town,
oval face with high cheekbones, fair skin, late twenties,
tall and lean, black bob, straight brows, dark eyes,
small nose, full lips, clean-shaven
```

（注意 `build` 的"tall and lean"与 `face` 的"oval face with high cheekbones"之间没有任何分隔语义——它们在模型眼里是同一层权重的东西。**"多高"和"鼻子什么样"被并列成了同级信息**，这正是清单式拼法的根问题。）

**这是一份设定表 token 清单，没有一个镜头词、光源词、环境词。**

参考图侧同样在把画面往人像上拉：[src/composables/useCharacters.ts:201](../src/composables/useCharacters.ts#L201) 的 `charRefSrcsOf` 固定 `front` 排第一，其余按 `CHARACTER_VIEWS` 顺序补。而 `front` 的定义是（[src/api.ts:2137](../src/api.ts#L2137)）：

```
single front-facing headshot of one person, head and shoulders fully in
frame with headroom above the head, neutral expression, plain background, centered
```

**"证件照 + 中性表情 + 纯背景 + 居中"就这样作为构图指令一起被送到了模型面前。** 模型最稳的解法就是"把参考图那张脸重画一遍"——环境当然融不进去。

### 2.1 为什么 120 字装不下（**这一上下限已在决定十里放宽**）

「自拍」这个词要变成画面，至少需要六件事：**谁在拍 / 相机在哪 / 什么镜头 / 光从哪来 / 时间是几点 / 背景里有什么**。而现在的 120 字要同时承担主题、机位、光影、环境、情绪——超出它一个数量级的容量。

装不下的部分模型会自己补默认值，而默认值就是：平光、平视、居中、纯背景。**死板不是模型的脾气，是缺省值。**

### 2.2 「自拍 / 他拍」在提示词里根本不存在

`photoSelf`（[src/lib/chatPhoto.ts:45](../src/lib/chatPhoto.ts#L45)）只决定**两件事**：拼不拼外貌、发不发参考图。它**没有任何镜头语言**。

更糟的一处：`self:` / `myself:` / `me:` 这三种前缀是**被剪掉**的（[server/chatTags.js:63](../server/chatTags.js#L63) 的 `SELF_STRIP_RE` / `SELF_MARK_RE`）。剪完之后只剩：

```
[photo:self:me on the balcony, hair down]   →   me on the balcony, hair down
```

于是它和 `[photo:a balcony]` 走到模型面前几乎没差别。**"自拍"这个意图在剪标签那一步就没了。**

（保留代词不剪的那种写法——`me at my desk`——虽然留下了主语，但那是一句"描述"，不是一句"机位"。它描述的是**画面里有什么**，不是**照片是怎么拍的**。两者不能互相替代。）

### 2.3 尺寸被降级成方框

[src/composables/useGeneration.ts:343](../src/composables/useGeneration.ts#L343)：

```ts
size: sizeForVendor(deps.config.value, 'auto')
```

`sizeForVendor`（[src/api.ts:358](../src/api.ts#L358)）的逻辑是：厂商认 `auto` 就发 `auto`，不认就退到 `allowed[0]`。而 `allowedSizes`（[src/api.ts:238](../src/api.ts#L238)）对只认枚举的厂商返回的就是那组固定尺寸，`allowed[0]` 通常是 `1024x1024`。

**横着拍的窗、竖着站的人，全被塞进同一个方框。** 而且这条降级链上没有任何"按内容挑"的余地——它连"这张图里有个人"都不知道。

### 2.4 另外两处静默损失

- **`quality` 永远不发**：`quality` 默认 `'auto'`，而 `extraParamsFor`（[src/api.ts:377](../src/api.ts#L377)）里 `quality !== 'auto'` 才带。对话这条路没有让用户选过，所以这一项对上游永远是缺席的。
- **改写能力没接上**：[server/enhancePrompts.js:27](../server/enhancePrompts.js#L27) 的 `quick` 档提示词里明明写着 "Add only what is missing and concrete: **lighting, material, color, lens, mood**"——这正是对话出图缺的东西，但对话这条路**完全没走 `/api/enhance`**（[src/composables/useGeneration.ts](../src/composables/useGeneration.ts) 里 `enhancePrompt` 只服务创作区输入框）。

### 2.5 一句话结论

**同一个 120 字的"场景名"既当主题、又当构图、又当灯光、又当环境、又当机位**（写这段时它还是 120 字，现在是 400 —— 但"一层不能承担五层"这个诊断没变）。** 它被要求承担的事远远超过它能承载的信息量。补哪一处缺省值都不解决问题——**缺的是"谁负责怎么拍"这一层**。

## 三、决定

### 决定一：拆开「是不是同一张脸」与「怎么拍」

现在这两件事被绑在一个布尔上（`self` 同时管拼外貌和发参考图）。要拆成两件独立的、各有默认值的事：

| 问题 | 谁回答 | 默认 |
| --- | --- | --- |
| 画面里有没有这个人 | 聊天模型的标签（已是现状） | 没有（场景照） |
| 这张照片**是怎么拍的** | **新增的摄影指导层** | 由场景推导，推不出就用中性第三人称 |

理由：把两件事绑在一起，等于说"只要它在画面里，构图就必须听设定表的"——而设定表里从来没有构图。

### 决定二：外貌从「token 清单」换成「锚点句」

**只锁骨相、发色发型与一个标识**，写进一句自然语言里；其余全部放开。

这是本文里**最反直觉、也最关键**的一条。`characterFaceDesc` 那二十个逗号短语之所以存在，是为了"场景一换就不是同一个人"——这个目标是对的。但它的代价从来没人算过：**那份清单同时也在锁表情、锁姿态、锁机位**。模型看到"neutral expression, plain background"级别的 token 密度，最省力的解法就是交一张证件照。

正确的分工是：

- **锁身份**：颧骨、脸型、发色与发型轮廓、一个标识（疤 / 义体 / 配饰）。
- **放开一切会随场景变的东西**：表情、视线、姿态、手在做什么、衣服的褶皱、光在脸上的方向、景深。

> 待定：锚点句的**字数上限**与"哪几项算不可变"需要定一份清单，落在 `CHAR_SPEC_LINES` 里（那已经是唯一权威定义，见 [server/charSpec.js:1](../server/charSpec.js#L1) 的说明）。**不要**另抄一份。

### 决定三：在标签与出图之间插一层「摄影指导」

这是治"没有光影、场景融不进去、自拍画成他拍"的**唯一位置**。

- **输入**：原始场景串 + 是不是它本人 + 锚点句。
- **输出**：一段分层提示词，固定按这个顺序（前段权重更高）：

  ```
  ① 介质      photographic, shot on a phone           ← 定"这是照片不是插画"
  ② 主体锚点  锚点句                                   ← 只锁身份
  ③ 镜头      自拍 / 他拍 / 特写 / 全身 / 过肩
  ④ 机位      前摄臂展 / 手持在胸前 / 第三人称平视 / 低角度
  ⑤ 光        光源、方向、时间、天气、色温
  ⑥ 环境      前景遮挡、中景主体、远景、景深
  ⑦ 动作情绪  它此刻在做什么、什么表情
  ```

- **落点**：接 `/api/enhance`（[server/index.js:924](../server/index.js#L924)）加一档 `photo`，或新增一个更窄的端点。**待定**：这一档是对外可配的文本模型，还是要用户显式打开（多一次调用 = 多一次延迟与花费）。
- **失败必须降级**：摄影指导失败时**不能**让这张图出不来，应退回"原始场景 + 模板"。这一条的约定与 [src/lib/chatPhoto.ts:34](../src/lib/chatPhoto.ts#L34) 那段"失败只返回 undefined，绝不 reject"是同一条纪律。

### 决定四：自拍 / 他拍各给一套硬模板

模板不是"更长的形容词堆"，而是两条固定的**机位句**：

| 镜头 | 模板要点 |
| --- | --- |
| **自拍** | 前置摄像头、臂展距离、脸部占画面上半、轻微广角畸变、手臂或手入画、脸被屏幕或环境光打亮、背景是它所在的地方且明显在近处 |
| **他拍** | 第三人称视角、机位不在它手上、环境**有纵深**（前景遮挡 / 中景主体 / 远景）、光源在画面里可见（窗、灯、天光） |

**为什么模板是必要的**：图像模型没有"自拍"这个概念的原生权重，它只有"画一个人"。"手机前置、臂展、畸变、手入画"这几个词才是**唯一**能把"画一个人"掰成"一张自拍"的东西。指望场景串里的一个 `me` 做到这件事是不可能的。

### 决定五：参考图与提示词分工，别互相打架

参考图**同时是"同一张脸"的唯一保证，又是最强的机位与光线污染源**——它是一张纯背景、平光、居中的证件照。现在这两件事没有被区分。

- 设定图**只在"要同一张脸"时才发**（现状已是对的）；发的时候只当**身份参考**，不当构图参考。
- 提示词里要**明确写出来**"只取这张脸，不要它的人像构图"，而不是指望模型自己理解——不写的话，模型默认会把参考图的构图一起继承。
- **选哪张参考图也要按镜头挑**（见决定六）。

### 决定六：参考图按镜头挑，不固定 headshot 优先

现在 `front` 永远排第一，其余按 `CHARACTER_VIEWS` 的固定顺序补。应该改成：

| 这张要拍什么 | 参考图 |
| --- | --- |
| 自拍 / 特写 / 半身 | `front` 打头 + 侧面或 3/4 |
| 全身 / 站姿 / 走 | 全身那张打头 + `front` |
| 纯场景（画面里没人） | **一张都不发**（现状已对） |

### 决定七：尺寸按内容挑，别一律方框

对话出图今天写死 `'auto'` 再被降级成方框。应该改成在**厂商能力表给定的枚举内**挑最接近的一档：

- 画面里有人 → 竖幅优先（`1024x1536` 一类）；
- 纯风景 / 窗 / 桌 → 横幅优先（`1536x1024` 一类）；
- 厂商只认正方形 → 用正方形，但**构图提示词要补偿**（写清"竖构图的全身入画"，让模型知道它是在方框里装一个竖幅场景）。

> 待定：这需要给 `sizeForVendor` 加一个"按内容挑、且挑不到就退到最接近档"的路径。**不要**把对话专用的尺寸偏好塞进 `FREE_SIZES`（[src/api.ts:263](../src/api.ts#L263)），那份表是给创作区下拉框用的。

### 决定八：`quality` 至少给一档显式值

现在这一项对上游永远缺席。对话出图应该给一档明确的 `quality`，而不是让厂商用它的默认档。**具体给哪一档待定**（要考虑不是每家都认这个名字，`extraParamsFor` 已经在按厂商能力拦了）。

### 决定九：视角归摄影指导判，聊天模型只回答"画面里有没有人"

**这一条是后加的**（2026-10-04，实现完第二批之后），它推翻了我原先在 §四 里的分工安排。

原先的分工是：聊天模型在标签里写 `self:` 表达"我在画面里"，客户端再拿 `isSelfie()` 的**词表**去场景串里找"自拍"这两个字，找不到就当第三人称。问题有两个：

1. **那是在用比模型更少的信息替模型做判断。** 词表只看得到那一行场景串，而"这张照片该谁拿相机"是个摄影判断；
2. **更糟的是这个判断随后被当成事实送出去** —— `directorTask` 会明确告诉摄影指导"这是第三人称，Keep that point of view，不许改"。于是它连纠正的机会都没有，我那个正则的错判被**固化**成了结论。

正确的拆法是按"谁知道什么"分：

| 问题 | 谁回答 | 为什么 |
| --- | --- | --- |
| 画面里有没有这个人 | **聊天模型**（`photoSelf` 布尔） | 只有它知道自己在描述什么。这是它**能可靠回答**的那一件事 |
| 这张照片该谁拿相机 | **摄影指导** | 它看得到整个场景，比一个词表更该做这个判断 |

**这条决定顺手消掉了一笔协议欠账。** §五 原先记着"自拍意图在剪标签时丢失，只能靠改协议解决"——现在不需要了：`photoSelf` 只承担"在不在画面里"（那件事它答得准），"怎么拍"交给下游模型推断。**协议一个字都不用改。**

`isSelfie()` 的词表**保留，但降级为没有摄影指导时的兜底**（没配文本模型、或那一跳失败）。词表仍然有用：它认得准明确写了"自拍"的场景，而那种场景恰好是猜错代价最大的。

**唯一一条不由摄影指导负责的护栏**：画面里没有人时，视角**只能**是空镜——一张"我看到的东西"里长出一个人，比视角选错严重得多。所以那条判据由 `photoSelf` 直接定死（见 `planChatPhoto` 的 `resolved`）。

### 决定十：放宽场景串与提示词上限，并把"扣尾"改成按标签起点算

**这一条是后加的**（2026-10-04），起因是一个被忽略的因果：**摄影指导只能看到那一行场景串**。它写得越薄，下游能推断出的东西越少——而它写的是 `leaning on the balcony` 这种只有主语加地点的东西。

所以改三处：

| 项 | 从 | 到 | 为什么 |
| --- | --- | --- | --- |
| 场景串上限 `PHOTO_SCENE_CHARS` | 120 | **400** | 120 字只装得下"在哪"，装不下时间/天气/周围有什么——而那些**恰好只有聊天模型看得见** |
| 提示词上限 `CHAT_PHOTO_PROMPT_CHARS` | 1200 | **6000** | 见下（这个不是保险起见，是**实测会被撞到**） |
| 系统提示里那一句 | "a short description… under 120 characters" | 明说该写时间/光/天气/周围/在做什么，并给了一个对照例子 | 不写清楚，模型就会继续交七个字 |
| 扣尾 `tailHold` | 返回"要扣住多少字符" | 返回"**可以放出去多长**" | 前者在标签开合之间不连续，一定会放错（详见 §九 第 9 条） |

**1200 那个上限是实测会被撞到的**，不是理论风险：拿一份最长的角色设定（锚点 220 字）+ 满 400 字的场景串跑一遍，底稿就已经 **1264 字**，摄影指导补完那几句之后是 **1586 字**。也就是说在放宽之前，**垫在最末尾的负面约束（挡"证件照"那套默认构图的话）会被无声砍掉**——而它正是这一整套改动想治的东西。6000 留了足够余量。

#### 但放宽场景串撞上了另一件事：扣尾

`TAG_HOLD` 原先是 `24 + PHOTO_SCENE_CHARS + 16 = 160`，即**按上限预留一整枚标签的长度**。场景上限提到 400 之后它会变成 440——**比一条角色的正常回复（一到三句）本身还长**，等于正文完全不流式：用户会盯着空白，直到整段回复写完。

根因是"按长度预留"这个做法本身：它假设"最坏情况下末尾可能有一整枚标签"，而**标签只可能出现在末尾**。所以改成按**它从哪开始**算（`tailHold`）：

- 判据是**最后一个还没闭合的 `[`**（`/\[[^\]\n]*$/`）。它还没闭合 → 整段扣住（`[pho`、`[photo:self:me on the bal` 都算）；已经闭合 → 那枚标签写完了，后面都是正文，一个也不用扣；
- `TAG_HOLD` 从"定值"降级为**地板**（24 字），管的是收尾那一瞬间的边界情况；
- 一个认不出来的 `[` 也不会永久扣住——超过 `TAG_MAX` 就按普通正文放出去。人话里出现一个方括号，不该让整条回复停住。

**这样放开标签长度就不再有任何延迟代价。** 单测里有一条专门量这件事：一段 30 字的正文后面跟 300 字的场景，正文必须**完整**放出去、且放出去的部分不含半个标签。

> 顺带纠正一个诊断里的说法：§2.1 写"120 字装不下"，容易被读成"把 120 放大就够了"。**不够。** 放宽上限只是让上游**能**写得更丰富；真正的分层是决定三那一套。两件事都得做。

## 四、这些信息谁来推断、什么时候推断
§三 决定"要补哪些层"，这一节决定**谁补、插在哪一步**。这不是风格问题——每个执行者能看到的上下文、能承受的延迟、以及失败后的代价都不一样。

### 4.1 三类信息，三类归属

**判据只有一条：做这个决定需要看到什么。**

| # | 信息 | 谁来做 | 为什么是它 | 什么时候 |
| --- | --- | --- | --- | --- |
| 1 | 时间与天气、它此刻在做什么 | **聊天模型**（现在就写标签的那次调用） | 只有它看得到对话与人格：用户上一句说"给我看看你"，这个"你"是什么意思只有它知道 | **流式中**（零额外延迟） |
| 2 | 介质、机位句、负面约束、尺寸与参考图选择 | **本地纯函数** | 全是查表与减法——给定一个视角就有唯一模板，不需要任何推断 | **出图前**（零延迟，不可能失败） |
| 3 | **视角（自拍 / 他拍）、镜头焦段、光的方向与色温、环境纵深、前景** | **摄影指导模型** | 视角与工艺都是摄影判断，聊天模型既写不好也不该分心去写 | **与骨架并行的后台** |
| 4 | 表情、视线、姿态 | **不预设，交给出图模型** | 上面三层一旦替它定死表情，就又回到证件照 | — |

第 4 行是这一节最要紧的一条：**顶层不许补表情**。"它此刻在做什么"由聊天模型给（第 1 行），但"嘴角什么弧度、眼睛看哪"是出图模型在场景里自己长出来的——我们再写一遍就等于又把它按死。

### 4.2 为什么不把推断全压在聊天模型身上

它能做第 1 行、也**只该**做第 1 行。三个理由，每一个都是硬的：

1. **它在流式里，标签是"扣住不发"的**（[server/chatTags.js:110](../server/chatTags.js#L110) 的 `TAG_HOLD`）。用户要等这串字符写完才看见正文。标签每加长一点，就是在**给正文加延迟**——一个每轮都付、直接可感知的成本。
2. **`TAG_HOLD = 24 + 120 + 16` 是按 120 这个上限算出来的**（[server/chatTags.js:110](../server/chatTags.js#L110)）。放宽场景上限就必须重算它，否则半截标签会漏给用户看——那是协议层最难看的一种失败。
3. **它的本职是人格与语气**（[server/index.js:169](../server/index.js#L169) 那一条"只写它会说出口的话"），温度还开到 0.9（[server/index.js:246](../server/index.js#L246)）。让它分心去想"焦段"，它写人格的注意力就被分走了。

**尤其不要让它写焦段。** 那是最容易被"编"出来的一项（`85mm f/1.4` 听起来很专业，但与场景毫无关系），而它对画面几乎只有坏处：一个乱写的焦段会把构图一起带偏。

### 4.3 模板必须"只补不覆盖"

第 2 行是**减法，不是加法**——这是整个补全设计里最容易做错的一处。

模板不能无脑写死 `warm afternoon light, shallow depth of field`：如果聊天模型已经在标签里写了"at dusk, rain on the glass"，模板再塞一句"暖光浅景深"就是**自相矛盾**，模型会挑一处当噪声丢掉，或者把两者硬凑成一张谁都不像的图。

正确行为是：

1. 先解析标签里**已经给出**了哪些（时间 / 天气 / 在做什么）；
2. 模板只补**空着**的位；
3. 一个位都没有内容可推时，**宁可留空**，也不要塞一个通用默认值——留空至少让出图模型按场景自己长，塞一个错的默认值比留空更糟。

### 4.4 什么时候发生：与流式的时间线对齐

```
聊天模型流式输出（含标签）
      │  ← 标签"扣在手里"，用户只看见正文
      ▼
[流末] splitTags 剪下 photo / photoSelf          server/chatTags.js
      │
      ▼
reply.photo 挂上，界面立刻占骨架位               App.vue:1552-1556
      │  ← 从这一刻起，正文已经完整可读，用户在等的是图
      ├──────────────────────────────┐
      ▼                              ▼
摄影指导调用（可选，带 timeout）     （什么都不做）
      │                              │
      └──────────┬───────────────────┘
                 ▼
        拼分层提示词（本地纯函数）              lib/chatPhoto.ts
                 │
                 ▼
        真正出图 → 贴到骨架上
```

**关键：摄影指导那一步和骨架并行，不在文字前面。** 图本来就比文字慢得多（[角色配图设计.md](角色配图设计.md) 坑 6 已经处理过一次这件事），多 1–2 秒的提示词改写淹没在出图的耗时里，用户几乎感觉不到。

### 4.5 推断失败怎么办

失败必须降级，**且降级发生在出图之前而不是之后**：

| 失败 | 处理 |
| --- | --- |
| 摄影指导超时 / 报错 | 退回"标签原文 + 模板"，**照画出图**（与 [lib/chatPhoto.ts:34](../src/lib/chatPhoto.ts#L34) 那段"失败只返回 undefined，绝不 reject"同一条纪律） |
| 模板与标签冲突 | 标签赢（它是从对话里来的，更可信） |
| 什么都推不出来 | 出一张中性第三人称的图，**不要**为了"有光影"塞一句假光 |

### 4.6 重画时怎么办

这一条容易漏，因为 [retryChatPhoto](src/App.vue#L1634) 是**从消息上重放**的：它只有 `photo` 与 `photoSelf` 两个字段（[src/App.vue:1634-1638](src/App.vue#L1634-L1638)）。

- 第 2 行（本地查表）是确定性的，**重放两次结果完全相同**，无问题；
- 第 3 行（摄影指导）不是。同一场景重放会得到不同提示词，也就是用户按一次"重试"会拿到一张构图不同的图。

三个选择：

1. **重画时跳过第 3 行**，只用第 1+2 行的确定性结果 —— 一致，但那一次的质量比第一次低；
2. **接受抖动** —— 简单，且"再来一张不一样的"对聊天场景未必是坏事；
3. **把改写结果存到消息上** —— 一致，但要动导出/导入的契约（[角色配图设计.md](角色配图设计.md) §三之二 那两个字段 `photo` / `photoSelf`），是一次协议改动。

> **倾向 1**：重画本来就是"上一次没画出来"的补救，用户要的是**一张图**，不是"和第一次一样的那张图"；而为了它新增一个落盘字段，代价明显大于收益。

### 4.7 三条不变量

无论最后怎么实现，这三条不能被破坏：

1. **补全永远不阻塞流式**。标签在写的时候就是延迟，所以它的预算必须小且固定；
2. **补全失败必须仍然能出图**。任何一层断掉都只降级、不返回空；
3. **补全不许改写主体**。第 3 行是"工艺"层，它改的是**怎么拍**；一旦它开始改"拍什么"，就等于把用户的话改写掉了——这是 [server/enhancePrompts.js:34](../server/enhancePrompts.js#L34) 那条 `Never swap the subject` 在出图这条路上的翻版。

## 五、需要改协议的那一条 —— **已结案：不需要改**

这一节原先记的是：「自拍 / 他拍」在剪标签时丢失（§2.2），**绕不过协议层**。当时的两个方向是：

1. 扩展 `[photo:…]` 标签，让聊天模型多写一个镜头词（`[photo:self:close:me on the balcony]`）；
2. 不改标签，让摄影指导层推导，`photoSelf` 的语义保持不变。

实现第二批时按**决定九**收口，结论是**方向 2，而且连"可选增强"都不需要了**：

| 原先担心的 | 现在的实情 |
| --- | --- |
| "用户明确要自拍"这种强意图只能靠场景文本传达 | 摄影指导看得到场景全文，它判视角就够了 —— 而聊天模型本来也一直在场景里写"自拍一张给你看"这类话 |
| 聊天模型若写错视角就固化了 | 它不再写视角了。`photoSelf` 只回答"在不在画面里"，那件事它答得准 |
| 老消息导回来会不会失效 | 不受影响。协议字段一个没动，`photo` / `photoSelf` 仍是全部依据 |

**所以这一节不再有欠账。** 留着它是为了记住这个结论是怎么来的：真正的问题从来不是"标签里少了一个字段"，而是**把一个该由下游模型做的判断，用客户端的一个词表提前做掉了，还把结果当事实告诉了下游**。

## 六、明确不做的

| 不做 | 为什么 |
| --- | --- |
| 不做「每张都重画角色设定图」 | 那是另一个功能的成本结构，而且设定图的立意就是**纯背景单张**，正好是本文要治的那种构图 |
| 不给外貌清单**再加字段**（更多 token） | §2.5 已经说清：问题不是清单太短，是它在管不该它管的事。继续加字段只会让画面更僵 |
| 不把改写档当成"可选的锦上添花" | 摄影指导这一层是**结构性缺失**，不是优化项。没有它，其余六条都只是缓解 |
| 不动 `TAG_HOLD` / 频率 / 落盘 | 与本文无关，见 [角色配图设计.md](角色配图设计.md) 的三之三 |

## 七、怎么验证

### 单测（纯函数，不需要联网）

- 分层提示词的**层序**：光/环境必须排在身份 token 之前（前段权重更高）；
- 自拍 / 他拍两条模板各自的关键词在位（"前置摄像头 / 臂展 / 手入画"与"第三人称 / 纵深"）；
- 锚点句的**取舍**：给定一份完整 `CharacterFields`，输出只含被判定为不可变的那几项，**表情与背景一个词都不许漏出去**；
- 摄影指导失败时的降级路径：返回的仍然是可用的提示词，**不是空串**；
- 参考图按镜头挑的映射表。

### 手测（同一场景、三个配置并排）

用同一句场景跑三种拼法，用图说话：

1. 现状（`scene + characterFaceDesc`）
2. 只换锚点句
3. 锚点句 + 摄影指导 + 模板

判定标准要**事先写下来**，否则很容易看完图就改标准：

- 有没有**可指认的光源方向**（脸上/身上有明暗面，不是平光）；
- 环境与人物有没有**接触关系**（影子落在地上、衣服被环境色染到、前景有遮挡）；
- 自拍的那张，**手或手臂有没有入画**、脸是不是被近处的光打亮；
- 不看提示词，能不能一眼分出哪张是自拍、哪张是他拍。

### 冒烟（确认降级链没坏）

- 对只认固定枚举尺寸的厂商发一张对话图：确认**没有非法的 size 值**发出去，且竖幅场景不再落回方框默认；
- 确认 `quality` 那一项按厂商能力表决定发不发（不认的厂商不能发）。

## 九、实现记录（2026-10-04）

两批都已落地。**没有改协议、没有碰落盘** —— 换掉的是"从标签到出图提示词"
这一段拼法，并让尺寸与参考图跟着镜头走。

- **第一批**（锚点句 / 分层 / 模板 / 尺寸 / 参考图）：零新增调用，纯替换拼法。
- **第二批**（摄影指导）：多一次文本调用，但它复用**已有的** `/api/enhance`
  端点与当前生效的文本配置，所以没有新端点、没有新配置项。

### 改了什么

**第二批（摄影指导层）另记一笔**，因为它的失败模式与第一批完全不同：

- **提示词**：`ENHANCE_PROMPTS.photo`，温度 `0.6`。服务端刻意**跳过** `REF_NOTE` 与
  `targetNote` —— 前者那句"不要重新描述整个场景"与它"补怎么拍"的职责直接冲突。
- **契约**：固定五行 `Shot:` / `Camera:` / `Lens:` / `Light:` / `Environment:`。
  要键值对而不是散文，是因为**已经说过的那一位要拒绝覆盖**，而那需要知道
  每一句属于哪一位 —— 散文做不到这件事。
- **`Shot:` 只认 `selfie` 与 `third` 两个词**（见 `parseDirectorShot`）。认不出就
  当作"它没判"，保留原视角 —— 归一化它的近义词（`portrait`、`close-up`）是在替它猜。
  它也是唯一一处**换一整套模板**而不是打补丁的输入：视角一变，
  medium / camera / lens / light / env / noPeople / action 全换。
- **验收**（`lib/photoDirector.ts`，纯函数）：带时间词的整行丢、带焦段的整行丢、
  结构字符抹掉、超长截断。丢整行而不是删掉那个词 —— 删完剩半句更糟。
- **降级**：逐位退回模板，不是整层。没配文本模型、调用失败、超时（15 秒）、
  五行一个都没认出来，都只是回退到第一批那套查表结果。

### 实现时改了主意的几处

**1. 锚点句不是"原来的清单加上镜头语言"，是直接做减法。**
原文写的是"给外貌补上镜头与环境锚点"，但真正动手时发现两件事是同源的：
那份清单**本身就是**画面发僵的原因。所以没有往 `characterFaceDesc` 上加东西，
而是新写了一个 `characterAnchor`，`characterFaceDesc` 一个字都没动 ——
创作区那条路继续用它（那里要的是"像素级约束"，目标不同）。

**2. 时间与天气不进模板。**
原计划的模板里有"时间/天气"位。实现时收掉了：那两样是**事实**，不是修辞，
场景没说几点，模板猜"黄昏"就可能和对话矛盾（它明明在值夜班）。
保留的只有一个**必然推论**：场景已经在下雨/下雪时，补一句"湿处反光"——
那是天气的下游事实，不是新事实。

**3. "环境纵深"不是"没说才补"。**
原计划把环境也做成"场景没说才补"，实现时发现那样等于没有：几乎每个场景
都会提过窗、桌、墙，于是纵深那句永远不出现。改成**无条件补** ——
它是相机原理（前景 / 中景 / 远景），与场景说了什么地点不冲突，
而它正是"人和环境融不进去"的药。

**4. `chatPhotoSize` 刻意**不**挑回 `auto`。**
`auto` 是"上游自己定比例"，而取景正是这一层刚做的决定 —— 挑回 `auto`
等于把自己刚做的决定又交出去。所以先在去掉 `auto` 的候选里按比例挑，
只有**一个显式比例都没有**时才退回 `auto`。

**5. `facialHair` 留在锚点句里，体型垫到最后。**
一开始把"clean-shaven"当成表情类的东西想剔掉，读回 `charSpec.js` 才发现
它的定位正相反 —— 那一栏的注释写着"必须始终显式写出来，留空会让模型
每张图猜得都不一样"。它是长相。于是顺序定为
脸 → 头发 → 眼睛 → 眉毛 → 鼻嘴 → 胡须 → **体型**：体型是唯一一项
"在大部分近景里根本看不见"的，触到上限时第一个出局。

**6. 空镜那句"画面里没有人"必须独立成层（做摄影指导时才发现的坑）。**
它原先并进 `camera` 那一层，而摄影指导会**整句替换** `camera` ——
于是空镜失去了唯一挡得住"风景里凭空长出一个人"的防线，而且**不会报错**。
现在它是独立的一层 `noPeople`（见 `chatPhoto.ts` 的 `ShotTemplate.noPeople`），
不在 `DIRECTOR_SLOTS` 里，摄影指导结构上就碰不到它。单测里有一条专门钉这件事。

**7. 摄影指导**不**接在出图后面，而是等它 —— 但不能等太久。**
文档 §四 里写的是"与骨架并行"。实现下来是**串行**：它改的就是出图要用的
那段提示词，并行没有意义（那是"先出图、再改图"才会有的结构）。
真正要紧的是**超时**：15 秒。用户看不到这一跳（界面上只有"图在画"），
所以卡住时宁可交一张模板拼的图，也不能让骨架一直转。

**8. 视角由摄影指导判之后，有一个"换个视角就得重拼"的坑。**
这是 §§ 决定九 落地时最不显然的一处：视角决定的**不是一句话，是一整套**
（medium / camera / lens / light / env / noPeople / action 全在这一套里）。
只把 `camera` 那一句换掉，会拼出一张"自称自拍、却按第三人称取景"的图 ——
因为自拍的 `medium` 是 `shot on a phone front camera`，那句话还在。

所以 `applyDirector` 里有一段是**重拼**而不是打补丁。重拼有两个容易写错的细节：

- **不能用已经解析过的视角当输入**。`plan.shot` 是结果，拿它当输入会把
  "场景里写着 selfie"与"模板用了 selfie"两种状态搅在一起 ——
  一旦它等于 `scene`，自拍那一套就再也回不来了；
- **锚点要原样带过去**。重拼会把它丢在原来的 layers 里，所以得先从
  `plan.layers` 里读回来。这里刻意不让调用方再传一次 anchor ——
  layers 本来就是"哪一层归谁管"的权威记录，另存一份只会多一处会漂的状态。

**9. 扣尾最后改成"放到哪"，而它是被端到端探针逼出来的。**
决定十 里已经写了前因（`TAG_HOLD` 不能跟着场景上限涨到 440），这里补的是
**怎么收敛的**，因为它推翻了我连续三版的写法：

| 版本 | 返回的量 | 怎么错的 |
| --- | --- | --- |
| 一 | `max(未闭合段长度, TAG_HOLD)` | 等于说"标签至少 24 字"，`[ph` 的保留点被抬到 24 —— **比 `[` 还靠后**，`[` 被放了出去 |
| 二 | `min(未闭合段长度, floor)` | 方向对了一半，但 floor=12 大于段长时只留 3 个字，**又把 `[` 推出保留区** |
| 三 | `max(floor, 未闭合段长度)` | 标签闭合那一瞬间这个量归零，**整枚标签被一次性放出去** |
| 四 | `min(完整标签起点, 未闭合 `[`)` | 两个候选取小 —— 超长场景里末尾刚冒出 `[` 时选中了它，**左边那枚完整标签被放出去** |
| **终** | **`放到哪`**：完整标签起点优先，没有它才用未闭合 `[` | 收敛 |

四版都错在同一件事上：**"扣多少"在标签开合之间不连续**。同一截缓冲，
标签没闭合时要整段扣住、闭合之后又要放出去 —— 而流到一半根本无从判断它
闭没闭合（整截缓冲**就是**那枚标签，后面还有没有正文只有流末才知道）。
"放到哪"是连续的：它就是标签的起点。

**这个结论单测没能自己发现**：前三版单测全绿。是 `scripts/probe-chat-photo.mjs`
按 3 个字符一块喂真流才暴露出来的。所以那一组单测现在全部按"分块喂"写，
而且两条最要紧的用例直接以"探针抓到的 bug"命名。

### 明确还没做

  （决定九），`photoSelf` 只回答"画面里有没有人"那件它答得准的事。
  原先以为"信息在源头丢了"，其实是**我一个客户端词表把判断提前做掉了** ——
  交给看得见整个场景的模型之后，这个缺口自己就没了。协议一个字没改。
- **`quality: 'high'` 是写死的**，不是用户可选项。当时没给这条加设置项，
  是为了不动参数面板；如果它证明不合适（例如某些厂商按 high 计费很贵），
  再考虑开一档。

#### 探针抓出来的三类 bug（单测当时全绿）

这一节记下来，因为它说明了那一百条单测**为什么不够**：

1. **两枚标签相邻时，上一枚完整标签被放了出去。** 判据里"末尾允许跳过标点"
   把上一枚的 `]` 当成了标点，边界于是跳过下一枚的 `[` 落到它上面。
   触发条件是**每一轮正常回复**（`[photo:…]` 紧跟 `[mood:…]`）。
2. **超长场景里"第一个换行之前"的那一段被当成了标签内容。** 字符类 `[^\]]*`
   跨过了换行，于是它右边判成"没有正文"，边界一路跑到前一枚标签前面。
3. **"扣多少"这个量本身选错了。** 前三版都在算它，三版都漏：
   这个量在标签**开合之间不连续**（没闭合要整段扣、闭合了又要放），
   而流到一半根本无从判断闭没闭合。改成算"**放到哪**"之后才收敛。

三个都只在**增量边界**上显形 —— 单测如果按整段一次性喂，永远测不出来。
所以 `tailHold` 那一组现在全部按"分块喂"写。这一条是这次改动里最值得记住的教训。

- **还没做的手测**：同一句场景前后各出一张图对比（§七 那三条判定标准：
  有没有可指认的光源方向 / 环境与人物有没有接触关系 / 能不能一眼分出
  自拍与他拍）。**这一条是判断改动有效性的唯一依据**，单测与探针只能保证
  "提示词拼得对、流式沒漏标签"，不能保证"图变好看了"。
- **探针还没覆盖的**：`/api/enhance` 打**真**上游的响应。探针里的假上游
  总是按五行回，所以"某个真模型不按格式回时会不会静默降级"仍然要手测一次。
