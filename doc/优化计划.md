# KImage 优化计划（Phase 0–3）

> 依据：[优化建议.md](优化建议.md)。
> 本轮范围：**Phase 0 数据安全 / Phase 1 传输体积 / Phase 2 消重复 / Phase 3 性能**。
> Phase 4 架构拆分与 Phase 5 产品项本轮不做（见文末）。
>
> 三条硬规矩：
> 1. 顺序按「损失不可逆程度」排 —— 会丢数据的先修，其次功能可用性，再次速度，最后架构；
> 2. 动大文件前先有护栏（测试）；
> 3. 每个任务独立提交、独立回滚，且必须写清**怎么验证**（测试用例或可复现手测步骤）。

图例：`[ ]` 未开始 · `[~]` 进行中 · `[x]` 已完成并验证

## Phase 0 · 数据安全

> 目标：不再静默丢用户的东西。唯一「现在不修，将来会挨骂」的一批。

- [x] **T0.1 测试基建**
  - 改动：引入 `vitest`，加 `npm test` 脚本；补 GitHub Actions 跑 `typecheck + test + build`
  - 验证：`npm test` 16 个用例通过；`npm run typecheck` 通过 · 提交 `def7a5c`
- [x] **T0.2 prune 保护「已标记」的图**
  - 现状：[idb.ts:843](../src/lib/idb.ts#L843) 的避让集合只认 `collectionId`，`marked` 完全不参与
  - 改动：把「含 marked 张的记录」并入避让集合；清理提示说明保留了几张；把「挑哪些该删」抽成纯函数 `planPrune` 便于测试
  - 验证：10 个用例 —— 含标记的最旧记录存活、清理窗口顺延、`keptMarked` 口径、count 边界 · 提交 `def7a5c`
- [x] **T0.3 写入路径的连接复用 + 体检节流**
  - 现状（校准后）：`addHistoryRecord` 每次都走 `pruneHistory`；其中 `openDB()` **每次都重新 `indexedDB.open()`**（无连接缓存），且每次都问一遍 `storage.estimate()`。占用超水位才全表读 —— 原文档「每次都全表扫」的说法不准确，已在 [优化建议.md](优化建议.md) 更正
  - 改动：缓存连接 `dbPromise`（`versionchange` 时关闭并清缓存、打开失败不缓存）；体检按「距上次 ≥ 30s 或新增 ≥ 20 条」节流，抽成纯函数 `shouldCheckStorage`
  - 验证：6 个用例覆盖首次必查、条数触发、时间触发、边界 · 提交见进度日志
- [ ] **T0.4 多标签页同步**
  - 现状：无 `storage` 监听、无 `BroadcastChannel`；`saveCharacters` 等是整份覆盖写
  - 改动：监听 `storage` 事件重载目录 + 提示「另一标签页已修改」
  - 验证：手测 —— 双标签页删角色不再复活；两页各建一条作品集互不覆盖

**风险**：T0.2 / T0.3 动的是删除路径。**测试先行**，新逻辑一律偏保守（拿不准就不删）。

## Phase 1 · 传输体积

> 目标：4K 图能真的用画布编辑。

- [ ] **T1.1 `/api/edit` 改二进制**
  - 现状：前端 [api.ts:894](../src/api.ts#L894) 走 JSON + data URL（膨胀 ~1.37×），撞服务端 [server/index.js:433](../server/index.js#L433) 的 15MB 上限
  - 改动：前端改 FormData 或直接提交 blob；服务端相应接收；出图那条路已走 multipart，可复用同一套解析
  - 验证：4K 图 + 同尺寸 mask 编辑成功（改前应失败）；记录改动前后的请求体大小
- [ ] **T1.2 尺寸策略归一**
  - 现状：参考图压缩（[App.vue:1327](../src/App.vue#L1327) 一带）与编辑的尺寸收窄各写一套
  - 改动：编辑保持原幅、参考图统一长边上限，收拢到一处
  - 验证：出图链路不回归（含角色双参考图那条路）

## Phase 2 · 消重复

> 目标：用最小风险砍掉两三百行同构代码，为将来的架构拆分铺路。

- [ ] **T2.1 抽 `lib/ui.ts`**
  - 现状：`trapTab` ×3（CharacterPage / ChatPage / ImagePreview）、「点外收起」×6、Esc 分层 ×7
  - 改动：`useFocusTrap` / `useOutsideClick` / `useEscLayers`
  - 验证：键盘与浮层逐条手测（Esc 逐层退、Tab 循环、关闭后焦点归还）
- [ ] **T2.2 抽 `pickActiveByKind`**
  - 现状：`App.vue` 的 `onMounted` 里四段同构约 60 行，且 `kind !== 'text'` 是硬编码
  - 改动：`pickActiveByKind(configs, kind, activeId)`，四类用途各调一次
  - 验证：单测 —— 存的 id 失效 / 用途被改 / 一条都没有，三种回退路径
- [ ] **T2.3 能力门控集中**
  - 现状：尺寸与扩展参数门控散在 `App.vue` 与 `api.ts` 两边
  - 改动：收到 `api.ts` 一处，界面只问「能不能」
  - 验证：单测覆盖 `autoSize` / `sizes:'free'` / Gemini 比例归一

## Phase 3 · 性能

> 目标：库变大后不劣化。**每项都要给出改动前后的实测数字，没有数字的性能改动不算完成。**

- [ ] **T3.1 历史页分页 / 虚拟滚动**
  - 现状：全量摊平渲染（[HistoryPage.vue:389](../src/components/HistoryPage.vue#L389)），500 条 ≈ 上千 `<img>`
  - 验证：500 条时 DOM 节点数、滚动帧率（前后对比）
- [ ] **T3.2 启动分页读取**
  - 现状：`loadHistory / loadPrompts / loadCharacters` 一次性 `getAll()`
  - 改动：先取最近 N 条，往前翻再读（交互心智历史页已有）
  - 验证：构造 500 条库，量首屏可交互时间（前后对比）
- [ ] **T3.3 `backfillThumbs` 空闲化**
  - 现状：对全部老记录逐张 canvas 重编码，首屏后持续占 CPU
  - 改动：串行 + `requestIdleCallback` + 可见优先 + 单次会话限量
  - 验证：首屏后 CPU 占用（前后对比）
- [ ] **T3.4 画布编码出主线程**
  - 现状：`toBlob` + data URL 在主线程，大图几百毫秒
  - 改动：`OffscreenCanvas` + Worker（或至少先让出一帧）
  - 验证：4K 图操作的输入延迟（前后对比）

## 本轮不做

| 项 | 为什么 |
| --- | --- |
| Phase 4 架构拆分（`App.vue` / `CharacterPage.vue` / `CanvasEditor.vue`） | 要等 Phase 0 的测试护栏就位；拆分本身不改行为，收益在长期 |
| Phase 5 · hash 路由深链 | 产品向，不阻塞上述优化 |
| Phase 5 · 公开部署鉴权 / 域名白名单 | 只在真的部署给别人用时才需要 |
| Phase 5 · i18n / 统一中文界面 | 同上 |
| Phase 5 · README + 文档引用改符号名 | 顺手做，不单独排期 |
