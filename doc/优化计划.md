# KImage 优化计划（Phase 0–3）

> 依据：[优化建议.md](优化建议.md)。
> 本轮范围：**Phase 0 数据安全 / Phase 1 传输体积 / Phase 2 消重复 / Phase 3 性能**。
> Phase 4 架构拆分与 Phase 5 产品项本轮不做（见文末）。
>
> 三条硬规矩：
> 1. 顺序按「损失不可逆程度」排 —— 会丢数据的先修，其次功能可用性，再次速度，最后架构；
> 2. 动大文件前先有护栏（测试）；
> 3. 每个任务独立提交、独立回滚，且必须写清**怎么验证**（测试用例或可复现手测步骤）。

图例：`[ ]` 未开始 · `[~]` 进行中 · `[x]` 已完成并验证

## Phase 0 · 数据安全

> 目标：不再静默丢用户的东西。唯一「现在不修，将来会挨骂」的一批。

- [x] **T0.1 测试基建**
  - 改动：引入 `vitest`，加 `npm test` 脚本；补 GitHub Actions 跑 `typecheck + test + build`
  - 验证：`npm test` 16 个用例通过；`npm run typecheck` 通过 · 提交 `def7a5c`
- [x] **T0.2 prune 保护「已标记」的图**
  - 现状：[idb.ts:843](../src/lib/idb.ts#L843) 的避让集合只认 `collectionId`，`marked` 完全不参与
  - 改动：把「含 marked 张的记录」并入避让集合；清理提示说明保留了几张；把「挑哪些该删」抽成纯函数 `planPrune` 便于测试
  - 验证：10 个用例 —— 含标记的最旧记录存活、清理窗口顺延、`keptMarked` 口径、count 边界 · 提交 `def7a5c`
- [x] **T0.3 写入路径的连接复用 + 体检节流**
  - 现状（校准后）：`addHistoryRecord` 每次都走 `pruneHistory`；其中 `openDB()` **每次都重新 `indexedDB.open()`**（无连接缓存），且每次都问一遍 `storage.estimate()`。占用超水位才全表读 —— 原文档「每次都全表扫」的说法不准确，已在 [优化建议.md](优化建议.md) 更正
  - 改动：缓存连接 `dbPromise`（`versionchange` 时关闭并清缓存、打开失败不缓存）；体检按「距上次 ≥ 30s 或新增 ≥ 20 条」节流，抽成纯函数 `shouldCheckStorage`
  - 验证：6 个用例覆盖首次必查、条数触发、时间触发、边界 · 提交见进度日志
- [x] **T0.4 多标签页同步**
  - 现状：无 `storage` 监听、无 `BroadcastChannel`；`saveCharacters` 等是整份覆盖写
  - 改动：新增 [lib/crossTab.ts](../src/lib/crossTab.ts) —— `syncTargetsOf(key)` 把 storage 事件映射成「要重载哪份目录」；`App.vue` 挂 `storage` 监听，重载配置/角色/作品集/提示词并提示一句；键常量从 `api.ts` 导入，不重抄字符串
  - 验证（单测 5 + 1 条防漂移）：键→目录映射、`key === null`（另一标签页 `clear()`）全量重载、不关心的键不触发；**防漂移用例读源码**，新增 localStorage 键若未纳入同步会让测试变红（已用假键验证过会红）
  - 验证（手测，需两个标签页）：
    1. `npm run dev` → 开两个标签页 A / B
    2. A 建角色 → B 弹「Updated from another tab — reloaded characters.」且列表出现该角色
    3. B 删该角色 → A 弹提示且它消失；**再在 A 保存任意角色，它不应复活**（这是本次要修的核心问题）
    4. A 在设置页删掉「当前生效」的配置 → B 应重挑一条，而不是让生效值悬空
    5. A 新建作品集 → B 的筛选器里出现它
    6. 反向：同一标签页里自己的保存**不应**弹提示

**风险**：T0.2 / T0.3 动的是删除路径。**测试先行**，新逻辑一律偏保守（拿不准就不删）。

## Phase 1 · 传输体积

> 目标：4K 图能真的用画布编辑。

- [x] **T1.1 编辑载荷收窄 + 超限时给人话**
  - 现状（实测，Pillow 生成同类内容测得）：画布把当前画面**一律编成 PNG 全分辨率**再 base64。一张 3840×2160 的照片编完是 **27.8MB**，而服务端请求体上限 15MB —— 在 4K 图上做局部编辑**必然失败**。而且厂商的编辑结果本身有上限（gpt-image-1 最大 1536、本站给的档位最大 2560），送 4K 进去换不到更大的结果
  - **方案调整（与原计划的「改二进制」不同）**：原计划是改传输协议（FormData/裸二进制）。实测后改用更省的路线 —— `lib/payload.ts` 里定长边上限 2560 与 8MB 预算，画布按内容选格式：

    | 内容 | 3840 PNG b64 | 2560 PNG b64 | 2560 JPEG b64 |
    | --- | --- | --- | --- |
    | 照片类 | 27.8 MB ❌ | 12.4 MB | **2.7 MB** |
    | 截图类 | 0.04 MB | **0.02 MB** | 1.1 MB |

    照片走 JPEG、带透明的走 PNG（JPEG 会把透明压成黑块），超预算再退一档（×0.7，下限 0.25）。这样不必新增依赖、不必自定义线格式，且**画质无损**：厂商的输出上限低于 2560，收窄不会换来更差的结果
  - 改动：新增 [lib/payload.ts](../src/lib/payload.ts)（纯函数：`dataUrlBytes` / `payloadScaleFor` / `shrinkScaleFor` / `payloadOverBudget`）；CanvasEditor 的 `editPayload` 让原图与 mask **共用同一个缩放系数**（尺寸不一致上游会判参数错误）；服务端补一条错误兜底，把 `entity.too.large` 与非法 JSON 翻成 JSON
  - 验证（单测 15 个）：字节折算、4K→2560 的比例、上下限、预算边界
  - 验证（服务端端到端，实起进程 + curl）：

    | 请求 | 改动前 | 改动后 |
    | --- | --- | --- |
    | 16MB 请求体 | **HTML 错误页 + 绝对路径堆栈**（前端只能显示 `Request failed (413)`） | `413 {"error":"The request body is too large","detail":"…up to 15mb…"}` |
    | 非法 JSON | HTML 错误页 + 堆栈 | `400 {"error":"The request body is not valid JSON"}` |
  - 验证（手测）：导入一张 4K 照片 → 套索局部重绘 → 应成功（改前必失败）；再用一张带透明的截图试「去背景」，确认透明没被压成黑底
  - 未做（留作后续）：真正的二进制传输。若将来需要 >2560 的编辑输入，再走那条路
- [x] **T1.2 尺寸策略归一**
  - 现状：「喂给模型的参考图」上限本来是**五处各写一个 1024**：首页参考图（[App.vue](../src/App.vue) 的 `compressImage(url, 1024)`）、`compressImage` 的默认参数、画布的 `REF_EDGE`、角色识图的 `VISION_MAX_EDGE`、聊天附图的 `CHAT_IMAGE_MAX`
  - 改动：收到 [lib/payload.ts](../src/lib/payload.ts) 一处 —— `REF_IMAGE_EDGE`（参考图）、`REF_ARCHIVE_EDGE`（只作复现凭据的存档）、`EDIT_PAYLOAD_EDGE`（编辑载荷），五处调用全部改用它；注释里的字面量也一并改成常量名
  - 验证（单测 3 条不变式）：参考图上限必须小于编辑载荷上限（两者取舍不同，不能混成一个数）；编辑载荷上限不得低于本站给出的最大档 2560（否则「选 2560 出图」会变成实际只送了更小的进去，且不报错）；三个数必须是正整数
  - **顺带发现（未修，记在这里）**：角色参考图那条路 [charRefSrcs](../src/App.vue) 最多送 4 张视图、**全程不压缩**，是唯一带「张数乘数」的参考图路径。按当前视图尺寸（≤1024×1536）估算约 8MB base64，仍在 15MB 以内，所以是**潜在风险而非现行缺陷**；真要修应该按字节预算而不是像素上限（压到 1024 会让全身视图掉到 683×1024，损失的是"像不像本人"这件事）

## Phase 2 · 消重复

> 目标：用最小风险砍掉两三百行同构代码，为将来的架构拆分铺路。

- [ ] **T2.1 抽 `lib/ui.ts`**
  - 现状：`trapTab` ×3（CharacterPage / ChatPage / ImagePreview）、「点外收起」×6、Esc 分层 ×7
  - 改动：`useFocusTrap` / `useOutsideClick` / `useEscLayers`
  - 验证：键盘与浮层逐条手测（Esc 逐层退、Tab 循环、关闭后焦点归还）
- [x] **T2.2 抽 `pickActiveByKind`**（提前到 T0.4 之前做：跨标签页同步要重挑「当前生效」，正好复用）
  - 现状：`App.vue` 的 `onMounted` 里四段同构约 60 行；`repickActive*` 四处各写一份 `find`
  - **顺带修掉一个真实缺陷**：出图那条的谓词写作 `kind !== 'text'`（`repickActiveImage` 是 `kind !== 'text' && kind !== 'vision'`），都漏了 `tts` —— 只配了一条朗读配置时，它会被挑成「当前出图配置」
  - 改动：`api.ts` 导出 `configKindOf` / `pickActiveByKind`，八处挑选统一走它
  - 验证：单测 9 个 —— id 命中 / id 失效 / 用途被改 / 老配置无 `kind` / 四类不串台 / 空列表；含「出图不会把 tts 挑进来」这条回归
- [ ] **T2.3 能力门控集中**
  - 现状：尺寸与扩展参数门控散在 `App.vue` 与 `api.ts` 两边
  - 改动：收到 `api.ts` 一处，界面只问「能不能」
  - 验证：单测覆盖 `autoSize` / `sizes:'free'` / Gemini 比例归一

## Phase 3 · 性能

> 目标：库变大后不劣化。**每项都要给出改动前后的实测数字，没有数字的性能改动不算完成。**

- [ ] **T3.1 历史页分页 / 虚拟滚动**
  - 现状：全量摊平渲染（[HistoryPage.vue:389](../src/components/HistoryPage.vue#L389)），500 条 ≈ 上千 `<img>`
  - 验证：500 条时 DOM 节点数、滚动帧率（前后对比）
- [ ] **T3.2 启动分页读取**
  - 现状：`loadHistory / loadPrompts / loadCharacters` 一次性 `getAll()`
  - 改动：先取最近 N 条，往前翻再读（交互心智历史页已有）
  - 验证：构造 500 条库，量首屏可交互时间（前后对比）
- [ ] **T3.3 `backfillThumbs` 空闲化**
  - 现状：对全部老记录逐张 canvas 重编码，首屏后持续占 CPU
  - 改动：串行 + `requestIdleCallback` + 可见优先 + 单次会话限量
  - 验证：首屏后 CPU 占用（前后对比）
- [ ] **T3.4 画布编码出主线程**
  - 现状：`toBlob` + data URL 在主线程，大图几百毫秒
  - 改动：`OffscreenCanvas` + Worker（或至少先让出一帧）
  - 验证：4K 图操作的输入延迟（前后对比）
