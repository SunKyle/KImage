> 依据：[优化建议.md](优化建议.md)。
> 本轮范围：**Phase 0 数据安全 / Phase 1 传输体积 / Phase 2 消重复 / Phase 3 性能**。

> 三条硬规矩：

## Phase 1 · 传输体积

> 目标：4K 图能真的用画布编辑。

- [x] **T1.1 编辑载荷收窄 + 超限时给人话**
  - 现状（实测，Pillow 生成同类内容测得）：画布把当前画面**一律编成 PNG 全分辨率**再 base64。一张 3840×2160 的照片编完是 **27.8MB**，而服务端请求体上限 15MB —— 在 4K 图上做局部编辑**必然失败**。而且厂商的编辑结果本身有上限（gpt-image-1 最大 1536、本站给的档位最大 2560），送 4K 进去换不到更大的结果
  - **方案调整（与原计划的「改二进制」不同）**：原计划是改传输协议（FormData/裸二进制）。实测后改用更省的路线 —— `lib/payload.ts` 里定长边上限 2560 与 8MB 预算，画布按内容选格式：

    | 内容 | 3840 PNG b64 | 2560 PNG b64 | 2560 JPEG b64 |
    | --- | --- | --- | --- |
    | 照片类 | 27.8 MB ❌ | 12.4 MB | **2.7 MB** |
    | 截图类 | 0.04 MB | **0.02 MB** | 1.1 MB |

    照片走 JPEG、带透明的走 PNG（JPEG 会把透明压成黑块），超预算再退一档（×0.7，下限 0.25）。这样不必新增依赖、不必自定义线格式，且**画质无损**：厂商的输出上限低于 2560，收窄不会换来更差的结果
  - 改动：新增 [lib/payload.ts](../src/lib/payload.ts)（纯函数：`dataUrlBytes` / `payloadScaleFor` / `shrinkScaleFor` / `payloadOverBudget`）；CanvasEditor 的 `editPayload` 让原图与 mask **共用同一个缩放系数**（尺寸不一致上游会判参数错误）；服务端补一条错误兜底，把 `entity.too.large` 与非法 JSON 翻成 JSON
  - 验证（单测 15 个）：字节折算、4K→2560 的比例、上下限、预算边界
  - 验证（服务端端到端，实起进程 + curl）：

    | 请求 | 改动前 | 改动后 |
    | --- | --- | --- |
    | 16MB 请求体 | **HTML 错误页 + 绝对路径堆栈**（前端只能显示 `Request failed (413)`） | `413 {"error":"The request body is too large","detail":"…up to 15mb…"}` |
    | 非法 JSON | HTML 错误页 + 堆栈 | `400 {"error":"The request body is not valid JSON"}` |
  - 验证（手测）：导入一张 4K 照片 → 套索局部重绘 → 应成功（改前必失败）；再用一张带透明的截图试「去背景」，确认透明没被压成黑底
  - 未做（留作后续）：真正的二进制传输。若将来需要 >2560 的编辑输入，再走那条路
- [x] **T1.2 尺寸策略归一**
  - 现状：「喂给模型的参考图」上限本来是**五处各写一个 1024**：首页参考图（[App.vue](../src/App.vue) 的 `compressImage(url, 1024)`）、`compressImage` 的默认参数、画布的 `REF_EDGE`、角色识图的 `VISION_MAX_EDGE`、聊天附图的 `CHAT_IMAGE_MAX`
  - 改动：收到 [lib/payload.ts](../src/lib/payload.ts) 一处 —— `REF_IMAGE_EDGE`（参考图）、`REF_ARCHIVE_EDGE`（只作复现凭据的存档）、`EDIT_PAYLOAD_EDGE`（编辑载荷），五处调用全部改用它；注释里的字面量也一并改成常量名
  - 验证（单测 3 条不变式）：参考图上限必须小于编辑载荷上限（两者取舍不同，不能混成一个数）；编辑载荷上限不得低于本站给出的最大档 2560（否则「选 2560 出图」会变成实际只送了更小的进去，且不报错）；三个数必须是正整数
  - **顺带发现（未修，记在这里）**：角色参考图那条路 [charRefSrcs](../src/App.vue) 最多送 4 张视图、**全程不压缩**，是唯一带「张数乘数」的参考图路径。按当前视图尺寸（≤1024×1536）估算约 8MB base64，仍在 15MB 以内，所以是**潜在风险而非现行缺陷**；真要修应该按字节预算而不是像素上限（压到 1024 会让全身视图掉到 683×1024，损失的是"像不像本人"这件事）

- [x] **T2.3 能力门控集中**
  - 现状：尺寸候选、默认档、手填尺寸归一、种子、扩展参数、逐模型尺寸校验、角色取景尺寸全都写在 `App.vue`，而它们只看厂商能力表，与界面无关；其中「按比例挑尺寸」还写了**两套度量**（编辑用对数距离、角色取景用差值）
  - 改动：全部收到 [api.ts](../src/api.ts) 一处并导出 —— `vendorOf` / `FREE_SIZES` / `normalizeSize` / `sizeOptionsFor` / `sizeIsFree` / `defaultSizeFor` / `sizeClosestTo` / `sizeForVendor` / `seedFor` / `extraParamsFor` / `acceptableSize`；`App.vue` 只剩「问一句能不能」与渲染
  - **写测试时抓出三个真问题**（都不是我原以为的样子）：
    1. **Gemini 的宽幅/竖幅档位根本不会生效**：候选里的 `1792x1024` / `1024x1792` 约分是 **7:4 / 4:7**，而服务端只认它自己那张比例表（含 16:9、9:16），于是选这两档时 `aspectRatio` **根本不发** —— Gemini 退回自己的 16:9 默认值。也就是说「选竖幅」以前拿到的是**横图**。已换成能干净约分的 `1536x864`（16:9）与 `864x1536`（9:16），并加了一条不变式测试：Gemini 的每一档都必须能约成服务端认的比例
    2. **平手被浮点末位决定**：`log(1.75)` 与 `|log(1/1.75)|` 只差 1.1e-16，同一组候选换个顺序就换个结果。已把差距量化到 1e-9，并留了一条判别用例（方图目标下横竖档同样远，平手由顺序决定 —— 换成差值度量就永远偏向竖档）
    3. **`auto` 的判定有两个来源**：厂商级 `autoSize` 与档位列表。`openai` 的 `autoSize` 是 true（那是给 gpt-image-1 的），而 `dall-e-3` 的档位列表里没有 auto —— 两处各判各的就会放行一个必被拒的值。已统一为「只看档位列表」
  - 顺带补掉一个洞：从提示词库/历史复现时套用 `auto`，落到认枚举尺寸的厂商（豆包、dall-e-3）上会被原样采用，而它们收到枚举外的值直接 400 —— 现在由 `acceptableSize` 拦下并保留当前值
  - 验证（单测 30 条，`api.test.ts` 共 39 条）：手填尺寸归一的容忍与拒绝、不认 auto 的厂商要摘掉 auto、OpenAI 两代模型的档位差异、不限尺寸厂商拿到常用值、Gemini 每档都能约分、默认档不能拿字面量 auto 当基线、按比例挑选（含平手判别）、逐模型退回第一档、种子（空/认不出/超范围/厂商不认/unknown 照发）、扩展参数门控、`acceptableSize` 四种情形
  - **有意的行为变化**：① Gemini 选 16:9 / 9:16 现在真的会发 `aspectRatio`（原来不发、竖幅退化成横图）；② 角色取景尺寸的度量从差值改为对数距离（只在平手时可能换一档）；③ 套用历史尺寸时不合法的值不再被采纳（保留当前值，而不是发出去被拒）
  - 端到端兜底：`npx vite build` 通过

> 用法（先起服务）：`npx vite preview --port 4173 &` 再
> `node scripts/measure-history.mjs --url http://localhost:4173/ --records 500`
> 也可当回归门用：加 `--max-dom-nodes 6000 --max-ms 400 --max-heap-mb 20`，超了就非零退出。

- [x] **T3.1 历史页分段渲染**

- [x] **T3.2 启动分页读取 —— 实测后判定「不做」**
  - 原计划：`loadHistory / loadPrompts / loadCharacters` 一次性 `getAll()` 改成先取最近 N 条
  - **实测结论：启动没有随库变大而劣化，不值得为此增加复杂度**

    | 库规模 | 启动到首页图墙首块 |
    | --- | --- |
    | 500 条 × 2 图 | 87.6 / 100.1 ms |
    | 2000 条 × 4 图（8000 张） | **104.9 ms** |

    原因：IndexedDB 反序列化记录时并不把图片字节读进 JS 堆（`Blob` 只是句柄），而首页图墙只渲染 12 块 —— "库变大就卡"的两个通常来源在这里都不成立
  - **更重要的理由：分页读会破坏筛选的正确性**。「Marked」与作品集筛选必须看到**完整**集合，只读最近 N 条会让筛选静默缺项、计数虚低。真要分页，得先有一张只存 `id / createdAt / marked / collectionId / prompt` 的轻量目录表（写入时维护），让筛选走目录、字节按需取 —— 那是一次带迁移的架构改动，不该在没有数据支撑时做
  - 触发条件（记在这里，够线再做）：启动到首块 > 300 ms，或记录数达到万级。届时按上面「轻量目录表」的路子做，并复用本轮的测量脚本验证
- [x] **T3.3 `backfillThumbs` 空闲化 —— 真正的问题不是卡，是慢**
  - 先量了再改：**主线程一个长任务都没有**（>50ms 才算，256/1024px 图都是 0 个）—— Chrome 的解码与编码本来就在别的线程，所以「逐张解码会卡住页面」这个前提不成立

    | 补好的缩略图 | 16 条 | **243 条**（≈15×） |

- [x] **T3.4 画布编码 —— 实测后判定：不需要 Worker，把同步 API 换掉就够了**
  - 探针实测（同一台机器，合成噪声图）：

    | 编码方式 | 主线程阻塞 | 产出 |
    | --- | --- | --- |
    | `toDataURL('image/jpeg')` 2560×1440 | **34.2 ms 全同步** | 1.77 MB |
    | `toDataURL('image/png')` 2560×1440 | **102.3 ms 全同步** | 9.08 MB |

  - 验证：探针数字（上表）+ `grep toDataURL` 在画布编辑路径只剩 64px 那处 + typecheck 与 106 个单测通过 + 全量复测无回归（历史页 3,016 节点 / 148 ms / 10 MB，均在预算内）

### A. 已完成/待做的收尾

- [x] **A1 缓存连接的健壮性**（Phase 3 之后补）
  - 问题：T0.3 把「每次重开连接」改成「缓存一个连接」之后，代码里只有 `onversionchange` 的清理，**没有 `onclose`、也没有死连接重试**。一旦连接意外关闭（浏览器回收存储、DevTools 清存储、IDB 后端异常），缓存就永久指向一个死连接，而每一处调用都把失败 catch 成「空」—— 表现正是代码注释里最怕的那句「我的图全没了」
  - 改动：[lib/idb.ts](../src/lib/idb.ts) 注册 `db.onclose` 清缓存；新增 `isDeadConnectionError` 与 `retryOnDeadConnection`（**只对「连接已死」重开重试一次**，别的原因重试没用、无限重试会把一次失败变成一次挂死），接进 `txStore`（覆盖 `getAll` / `putOne` / `deleteOne`）与 `pruneHistory` 的读与删
  - 验证（单测 9 条）：错误判定（InvalidStateError / DatabaseClosedError / 其它错误不算 / 退化输入不抛）；重试语义（正常只开一次、死了重开一次并成功、重试仍失败如实抛出、非死连接错误不重试、异步失败同样触发重试）
  - 验证（真浏览器，[measure-history.mjs](../scripts/measure-history.mjs) 新增 `--probe-reopen`）：标记一张图触发写 → 从页面里 `deleteDatabase` → `deleteResult: "success"`（**1.8ms 就让开，不是 blocked/timeout**）→ 再写一次 → `recordsAfterReopen: 1`（**重新开库、重建表结构、写成功**）
  - 覆盖边界（如实记下）：`onclose` 与重试是单测覆盖的；`versionchange` 让位与重开是浏览器端到端覆盖的。**「连接在事务中途死掉」不在重试范围内** —— 那种情况 IndexedDB 给的是 AbortError，盲目重放一个多步事务并不安全
